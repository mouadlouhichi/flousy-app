## 1. Verdict

The engineering baseline is genuinely strong: server-side authorization is the
boundary (not the UI), the money engine is conservation-based with an immutable
ledger and revision-checked writes, secrets never reach the browser, and every
public endpoint is authenticated and/or rate-limited. There is **no critical
finding** in this pass.

What remains is a set of **medium and low findings**, mostly at the seams:
(a) two RBAC gaps where the client asks for something the rules will refuse
(a broken screen, not a privilege escalation), (b) one real read-scope
over-grant on the invoices collection, (c) email-casing fragility in the
invitation claim path, and (d) rate limits and dedupe caches that are
per-instance for one endpoint. Details and fixes below.

Severity key: **H** = fix before/at launch · **M** = fix soon · **L** = polish.

## 2. RBAC audit

### 2.1 The model, as implemented

Two authorization layers that are meant to mirror each other:

- **Client**: `src/lib/household-rbac.ts` — 11 areas × 4 levels
  (`none|view|editOwn|editAll`), clamped by `sanitizePermissions()` against
  `AREA_LEVEL_OPTIONS`, resolved once by `resolveAreaAccess()` and consumed via
  `useHousehold()` (`areaLevel` / `canViewArea` / `canEditArea`).
- **Server**: `firestore.rules` — `validCustomPermissions()` mirrors
  `AREA_LEVEL_OPTIONS` key-for-key, and `customMonthChangesGranted()` enforces
  per-area grants on the *shared month document* by diffing
  `affectedKeys()`. This is unusually good; most apps stop at document-level
  role checks.

Roles: `owner` (full, only role that can manage members/settings/delete),
`editor` (full finance, `view` on members/settings), `viewer` (read all, no
invoices), `contributor` (invoices `editOwn` only), `custom` (matrix),
`profile` (a non-user placeholder for settle-up attribution).

Cross-checked and **confirmed consistent**:

| Guarantee | Client | Rules |
| --- | --- | --- |
| `members`/`settings` never exceed `view` | `AREA_LEVEL_OPTIONS` | `validCustomPermissions()` |
| `invoices` tops out at `editOwn` | same | same |
| Month edit needs `editAll` on that area | `hasMonthEditGrant` | `customMonthChangesGranted` |
| Entitlement lapse ⇒ read-only, never data loss | `areaAccess` downgrade to `view`, exports preserved | `householdEntitled()` on every write gate |
| Role escalation to `owner` via update | not offered | `before.role != 'owner'` + create-only owner branch |
| Custom member joins with self-authored grants | — | `invitationJoinOk()` requires `permissions == invite.permissions` |

### 2.2 Findings

**R1 (M) — `invoices` list/get is over-granted to every editor and to `custom`
members with `invoices: 'view'`, including *other members'* receipts.**
`firestore.rules` (invoices `get`/`list`):

```
allow list: if householdEditor(hid)
  || (customMember(hid) && customLevel(hid,'invoices') == 'view')
  || (householdMember(hid) && resource.data.submitterId == request.auth.uid);
```

For a `list`, `resource.data` is evaluated per document, so the third clause is
the correct "own invoices only" scope — good. But the *second* clause gives a
`custom` member with a mere `view` grant the whole household queue, which
includes `receiptUrl` (a base64 receipt image up to 120 KB) submitted by every
other member. `view` on invoices is documented as "read the household queue", so
this is by design — but it is the single broadest read grant a non-editor can
hold, and receipts are the most sensitive artifact in the app.
*Recommendation:* either split the area into `invoices` (own) and
`invoicesQueue` (all), or drop `receiptUrl` from what a `view`-only custom
member can read (would require storing receipts in a subdocument).

**R2 (M) — A `contributor` (or invoices-only `custom` member) cannot read the
member roster the client asks it to read.**
`members` `list` is `householdFinanceReader(hid) || householdOwner(hid)`, and
`householdFinanceReader` is `owner|editor|viewer` only. But
`src/lib/household-context.tsx:203` subscribes `subscribeHouseholdMembers()`
unconditionally for any tracked household. For a contributor the listener errors,
`db.ts:1311` swallows it into `onData([])`, and then:

- `myMember` is `undefined` ⇒ `memberRole` is `undefined` ⇒
  `permissionsFor(undefined)` returns **all-`none`**;
- `isContributor` is computed from `memberRole` and is therefore **false**;
- so the provider takes the *non-contributor* branch at
  `dashboard-provider.tsx:623` and subscribes the household month document,
  which rules also deny.

Net effect: a contributor lands in a household workspace with everything hidden
(`AreaRestricted` everywhere), the invoice-submission form suppressed
(`contributor-invoice-form.tsx:31` requires `areaLevel(invoices) === 'editOwn'`),
and a console full of permission-denied — i.e. **the contributor role's only
feature is unreachable from a cold load**. It is a functional break, not an
escalation, but it silently disables a shipped role.
*Fix (either side works, do both):*
1. rules — allow `list` on `members` for any active member, or at minimum allow a
   member to `get` their own row (the `get` rule already permits
   `memberId == request.auth.uid`, so the client just needs to use it); and
2. client — fetch `members/{uid}` directly with `getHouseholdMember()` (already
   exists, `db.ts:1376`) to establish `myMember`, and only fall back to the full
   roster when `canViewArea('members')`.

**R3 (M) — `isOwner` is partly derived from a client-visible, non-authoritative
field.** `household-context.tsx:219`:

```ts
const isOwner = Boolean(household?.ownerId === user?.uid
  || household?.planOwnerId === user?.uid
  || myMember?.role === 'owner');
```

Rules treat only `ownerId` as ownership (`householdUpdateAuthorized` compares
`before.ownerId`), and `planOwnerId` is merely the *billing sponsor*. A household
where the two diverge (legacy documents; the sponsor-rebinding repair path) gives
the sponsor a full owner UI whose writes the server refuses. No data is exposed
(reads are still rules-gated) but every management action fails with a generic
error. *Fix:* drop `planOwnerId` from the `isOwner` derivation; keep it only for
entitlement resolution.

**R4 (L) — `profile` role is invitable at the rules layer but not at the client.**
`memberCreateAuthorized` accepts `role in [... 'custom', 'profile']` for the
owner-creates-member branch, while `InviteRole` excludes it. That is intentional
(placeholders for settle-up), but `permissionsFor('profile')` falls through to
`none()` — worth an explicit early-return so a future refactor can't make
`profile` inherit a default.

**R5 (L) — `LEGACY_CUSTOM_FALLBACK` is client-only.** A `custom` member document
with no stored `permissions` gets `invoices: 'editOwn'` in the UI, but rules read
`permissions.get(area,'none')` and grant nothing. Same class of bug as R2:
UI offers an action the server refuses. Either backfill the map with a migration
or make the fallback a no-op and tell the user to ask the owner to re-set grants.

### 2.3 What is correctly enforced (verified, worth keeping)

- Owner-only: household `delete`, member `delete` (and never an `owner` row),
  invite `create`/`revoke`/`delete`, month `delete`, period **reopen**
  (`monthUpdateAuthorized` requires `access.owner` whenever the period is closed).
- Invoice approval is atomic and cannot be faked: the status change must be
  accompanied by the month document carrying `lastMutationId ==
  'invoice-approval-<id>'` with a `revision` exactly one higher
  (`invoicePostedMonthOk`). A status-only approval is refused, and the emulator
  suite asserts exactly this.
- The launch trial is a one-shot, server-time-validated 90-day window
  (`validLaunchTrialClaim`) with `affectedKeys().hasOnly(...)`; all other
  entitlement fields are immutable to browser clients — the projection for a
  household can never exceed the sponsor's own profile
  (`entitlementProjectionAgrees`).
- Rules are **total by construction** (every read is `get(key, default)`,
  every path guarded by `exists()`), and CI enforces both that property
  (`scripts/rules-totality.mjs` + a baseline) and the 1000-expression budget
  (`scripts/rules-budget.mjs`). This is the most mature part of the repo.

## 3. Security audit

### 3.1 Findings

**S1 (M) — `/api/barcode/lookup` uses its own in-memory limiter, not the shared
one.** Every other route uses `isRateLimited()` from `src/lib/server/rate-limit.ts`
(Upstash-backed when configured). This route keeps a private `hitsByIp` Map
(`route.ts:68`), so on serverless the real limit is 60/min **per instance**, reset
on every cold start, and it never becomes durable when Upstash is configured. It is
also the only public route with no Arcjet check, and each miss can fan out to five
upstream hosts for up to 12 s. *Fix:* swap in `await isRateLimited('barcode', ip,
60, 60_000)` and add `checkArcjet(request)`.

**S2 (M) — the contact-form dedupe cache is per-instance.** `seenRequestIds`
(`api/contact/route.ts:34`) is a module-level Map, so an honest client retry that
lands on a different lambda sends a second email. Move it behind the same Redis
limiter (a `SET NX` on `contact:req:<id>`), or accept the duplicate and document it.

**S3 (M) — invitation acceptance is case-sensitive on email.** Rules compare
`resource.data.email == request.auth.token.email` verbatim; the client stores
`email.trim().toLowerCase()` (`household-context.tsx:359`) and queries with
`.toLowerCase()` (`db.ts:1756`). Firebase does *not* guarantee a lowercased
`email` claim for every provider/import path. When the token carries
`Foo@Example.com`, invite discovery returns nothing and the accept batch is
denied — indistinguishable from an expired invite. *Fix:* compare
`request.auth.token.email.lower()` in the three `householdInvites` rules and in
the `members` `get` rule, and lowercase on write everywhere (already done client
side).

**S4 (M, accepted-with-caveat) — CSP keeps `script-src 'unsafe-inline'`.** The
tradeoff is documented in `src/proxy.ts` (nonces would force all 36 prerendered
routes dynamic) and mitigated well: `script-src-attr 'none'`, `object-src 'none'`,
`base-uri`/`form-action 'self'`, `frame-ancestors 'none'` in production. The
residual risk is real but small because the app renders no user-authored HTML —
the one place raw markup is emitted, `JsonLd`, escapes `<`, and both inline
scripts in `layout.tsx` / `install-prompt-capture.tsx` are static literals. I
would only revisit this when Next.js supports hash-based CSP.
*One thing to tighten now:* `img-src 'self' data: https:` allows any HTTPS image
origin; avatars accept `https://…` from the identity provider
(`profile-avatar.ts:25`), so this could be narrowed to
`'self' data: https://lh3.googleusercontent.com` and friends.

**S5 (L) — `frame-ancestors *` off-production.** Deliberate (preview panes) and it
fails closed whenever `NODE_ENV !== 'development'`, but note that a Vercel
*preview* deployment builds with `NODE_ENV=production`, so previews are sealed —
good. No action; recorded so it isn't "fixed" the wrong way later.

**S6 (L) — `verifyFirebaseIdToken` fails open on revocation-check transport
errors.** Correct posture (signature + `exp` already prove the token) and clearly
documented, but it means a revoked session stays usable for up to an hour if
Identity Toolkit is unreachable. Acceptable for an invitation-email endpoint;
would not be for a money-moving one.

**S7 (L) — receipts and avatars are base64 inside Firestore documents.** Bounded
(`receiptUrl` ≤ 120 000 chars in rules, avatar ≤ 140 000 client-side), so no DoS,
but it means every reader of a month/invoice document downloads images they may
not need, and it couples image retention to document retention. Firebase Storage
with signed URLs is the eventual answer.

**S8 (L) — client error beacon can carry PII in a stack/message.** `/api/client-errors`
clips fields and never stores them, but forwards to Sentry/Better Stack when keyed.
Fine; just make sure the privacy page says so (it currently describes analytics
consent, not error telemetry).

### 3.2 Confirmed good

- No secrets in the browser bundle: `RESEND_API_KEY`, `ARCJET_KEY`, Upstash and
  Sentry keys are read only in `runtime = 'nodejs'` route handlers.
- No `firebase-admin` and no service-account key in the app runtime — ID tokens
  are verified against Google's published certs with `alg` pinned to RS256
  (the `none`-algorithm bypass is explicitly refused) and `iss`/`aud` pinned to
  the project.
- `/api/household-invitations` reads the invite **with the caller's own token**
  through the Firestore REST API, so the rules decide what can be mailed; the
  request body supplies only an id. Recipient, role and household name are never
  taken from the client. The accept URL comes from `APP_URL`, never from the
  request `Host`.
- Contact form: honeypot, per-IP limit, Arcjet, HTML-escaped body, truthful 503
  when unconfigured, and a hard refusal to send from the Resend sandbox domain in
  production.
- Headers: HSTS w/ preload, `nosniff`, COOP `same-origin-allow-popups`,
  CORP `same-origin` (with a deliberate carve-out for social/icon assets),
  `Permissions-Policy` allowing only `camera=(self)`, `poweredByHeader: false`.
  Private routes are `private, no-store`; `/api/*` is `no-store`; the service
  worker never caches `/api`, Firestore, Auth or identity traffic.
- Account deletion is truthful: `deletionTracker()` reports per-step failures, the
  profile document (which is also the retry manifest of household ids) is kept if
  any earlier step failed, and leaving someone else's household retires the
  membership row instead of destroying the owner's data.
- `npm audit --omit=dev` is a CI gate that distinguishes "real advisory" from
  "advisory service unreachable" — a detail most repos get wrong.

## 4. Functional audit

### 4.1 Findings

**F1 (M) — the contributor cold-load break.** See **R2**. Functionally this is the
most impactful item in the whole audit: a role you can invite people into does not
work on first load.

**F2 (M) — a contributor cannot see the status of their own submissions.**
Rules explicitly allow it (`submitterId == request.auth.uid` on `get` *and*
`list`), but no client code subscribes: `subscribeHouseholdInvoices` is called
only from `household-invoice-review.tsx`, and only when `canEditArea(invoices)`.
So a contributor submits a receipt into a void — no "pending / approved /
rejected", no way to delete a mistaken submission (which rules also allow while
`status == 'submitted'`). This is a small, high-value feature the backend is
already fully built for.

**F3 (M) — sponsor/owner divergence produces an owner UI that cannot write.**
See **R3**.

**F4 (L) — permission-denied on the members listener is swallowed silently.**
`db.ts:1311` logs and calls `onData([])`, which is what makes F1 present as
"everything is empty" rather than "you don't have access". Mirror the
`subscribeHousehold` treatment: surface `denied` vs `unavailable` so the UI can
say which it is.

**F5 (L) — invoice approval picks the target month from `household.monthStartDate`
at review time.** If the owner changes the month start date between submission and
approval, an invoice can post into a different period than the contributor saw.
Rules only check that the named month is consistent, so this is a product
decision, not a hole — but showing the target period in the review row would make
it visible.

**F6 (L) — `AREA_LEVEL_OPTIONS` offers no `editOwn` for expense areas** because
rules cannot attribute rows inside a shared month document. Correctly reasoned and
documented; noting it because "let this person add expenses but only edit their
own" is the most obvious thing a household owner will ask for next, and it needs a
per-row `createdByUserId` check that the current document shape can't enforce.

### 4.2 Confirmed good

- Money engine: refund-then-charge on edits, `MoneyInvariantError` guards, cent
  rounding with the savings envelope absorbing remainders, deterministic
  recurring-template IDs (no duplicates on retry), IndexedDB outbox with explicit
  conflict/retry/discard states, monotonic `revision` + immutable ledger row per
  mutation, and an idempotent replay contract enforced by rules
  (`mutationTargetAgrees`).
- Period model: configurable start day, period-bound expense dates, close/reopen
  with rules-enforced read-only state and a currency snapshot per period.
- Entitlement expiry never hides or deletes data — the workspace goes read-only
  and **exports stay available** (`exportSections` deliberately survives the
  downgrade). That is the right call and it is implemented, not just stated.
- Honest degradation everywhere an external service may be missing: contact and
  invitation endpoints return a machine-readable `code` + a hint naming the exact
  env var, instead of faking success.
- i18n: en/fr/ar with a catalog-parity test, RTL handled with a pre-paint inline
  script so an Arabic session never flashes LTR.

| 6 | M | Contact dedupe → Redis | `api/contact/route.ts:34` |

| 8 | L | Narrow `img-src`; surface members-listener denial; `permissionsFor('profile')` explicit; document error telemetry in the privacy page | various |

None of these block a launch on their own; **#1 and #2 together are what make the
contributor role real**, and #3 is the kind of bug that will look like "invitations
are broken" for a small fraction of users with no way to diagnose it.

## 6. Note on the rules emulator

`npm run test:rules` could not run here (no JVM in the sandbox). Given how much of
this application's security depends on `firestore.rules`, and that the file is
1121 lines with a hard 1000-expression evaluation budget, **that CI job is the
release gate** — nothing in this report substitutes for it. Any of the rules
changes proposed above must be re-run through it, and #1 and #3 in particular
should each land with a new emulator case.
