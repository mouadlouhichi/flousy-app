# PART B — Deeper functional audit (new findings)

Everything in this part was found by **executing** the engine, not reading it.

## B.1 New functional findings

### F-new-1 🟥 The needs/wants keyword matcher is still wrong on 12 of 20 realistic categories

The `categoryEnvelopes` override landed (and survives rollover — I verified the
seed carries it), but it only helps categories the user explicitly classifies.
Everything else still falls through to `bucketOf()`, which is unchanged.
Re-ran the prior audit's exact matrix:

```
keyword accuracy: 8/20 correct, 12 wrong
WRONG  Medicine (variable)    -> wants, expected needs
WRONG  Médicaments (variable) -> wants, expected needs
WRONG  Doctor / Dentist       -> wants, expected needs
WRONG  School fees / Crèche / حضانة -> wants, expected needs
WRONG  Electricity (variable) -> wants, expected needs
WRONG  Baby diapers           -> wants, expected needs
WRONG  Disney+ / Shahid VIP / Canal+ (fixed) -> needs, expected wants
```

Two aggravating factors confirmed in code:

1. **The override UI reaches only one surface.** `handleSetCategoryEnvelope` is
   exposed by the provider but consumed **only** by `variable-screen.tsx:30`
   (and gated on `canEditArea('settings')`). A user who never opens that
   specific control never classifies anything, and fixed bills — where
   `Disney+ → needs` is wrong — have no override entry point at all.
2. **Renaming a category silently re-buckets all history**, because
   `envelopeFor()` falls back to the name whenever no override is stored.

This skews the 50/30/20 bars on the Overview screen — the app's primary
visualisation. *Fix:* seed `categoryEnvelopes` for **every** category at
creation/normalisation time (so the guess is frozen once, not re-derived), and
surface the needs/wants toggle in the category manager and the fixed-bill modal.

### F-new-2 🟥 A carried debt and its original are two independent records that silently diverge

`carryOverDebts()` deep-copies the debt (including `payments`) into the new
month. Nothing links them afterwards except the informational `carriedFromId`.
Executed proof:

```
aug outstanding: 2500     # after paying 500 in August, against the original d1
sep outstanding: 2000     # after paying 1000 in September, against debt-carry-d1-2026-09
-> the user owes 1500; the two documents claim 2500 and 2000
```

Both edits are legitimate in the UI: the Debts tab renders the debt of whichever
month you are viewing, and a back-dated payment against last month's copy is a
normal correction. There is no reconciliation, no "this debt lives in another
period" indicator, and the carry is not re-run on the already-materialised
September document — so the August payment never propagates. Worse, if the
September document had *not* yet been created, re-running the carry copies the
August payment forward and the September payment is lost from the chain.

This is the same class of problem the prior audit identified (debts inside the
month document), only moved one step: F-1 fixed *visibility* across periods,
not *identity*. The clean answer remains option 1 from that audit — a global
`users/{uid}/data/debts` document mirroring savings goals, with payments posting
a cash movement into the month where they fall. As a cheap interim: make the
carried copy authoritative and render prior-period copies read-only.

### F-new-3 🟧 A bill due on the 29th/30th/31st silently disappears from "upcoming" in short months

`getUpcomingBills()` builds the due date with
`Date.UTC(year, month, day)` (store.ts:742). JavaScript **overflows** that into
the next month — `Date.UTC(2026, 8, 31)` is `2026-10-01` — and the very next
line, `if (end && due > end) continue;`, then discards it. Executed over all of
2026 with a rent bill due on the 31st:

```
months where a 31st bill NEVER appears: 2026-02, 2026-04, 2026-06, 2026-09, 2026-11
months where it appears in the wrong month: none
```

So in the five short months of the year the bill is simply absent from the
Overview "upcoming bills" card **and** from the notification centre. The
`DueDayPicker` custom input accepts 1–31, so users can and will pick these days
(rent and salary-advance repayments on the 30th are common). The existing test
(`envelope-debts.test.ts:177`) covers the shifted-period case but never a day
that does not exist in the target month.

*Fix:* clamp to the month's last day —
`Math.min(day, new Date(Date.UTC(y, mo + 1, 0)).getUTCDate())` — which is also
what a bank does with a 31st standing order. Add the four-month regression.

### F-new-4 🟧 Contributor cold-load: the role's only feature is unreachable

*(This is both a functional and an RBAC finding; the RBAC mechanics are R2 below.)*
`household-context.tsx:203` subscribes `subscribeHouseholdMembers()` for any
tracked household, but rules restrict `members` `list` to
`householdFinanceReader` (owner/editor/viewer) or the owner. For a contributor
the listener is denied, `db.ts:1311` swallows the error into `onData([])`, so
`myMember` is `undefined` → `memberRole` is `undefined` → `permissionsFor(undefined)`
returns all-`none` → `isContributor` computes **false** → the provider takes the
non-contributor branch at `dashboard-provider.tsx:623` and subscribes the
household month document, which is also denied.

Net effect: everything renders as `AreaRestricted`, and
`contributor-invoice-form.tsx:31` (which requires `areaLevel(invoices) === 'editOwn'`)
suppresses the submission form. A role you can invite people into does not work.

### F-new-5 🟧 Contributors cannot see the status of their own submissions

`firestore.rules` explicitly permits it — the invoices `get` **and** `list`
rules both carry `householdMember(hid) && resource.data.submitterId == request.auth.uid`,
and `delete` is allowed while `status == 'submitted'`. No client code uses it:
`subscribeHouseholdInvoices` is called only from `household-invoice-review.tsx`,
and only when `canEditArea(invoices)`. A contributor submits a receipt into a
void — no pending/approved/rejected state, no way to withdraw a mistake. The
backend for this feature is already built and tested.

### F-new-6 🟨 `isOwner` includes `planOwnerId`, which rules never treat as ownership

`household-context.tsx:219` ORs `ownerId`, `planOwnerId` and `myMember.role === 'owner'`.
`householdUpdateAuthorized()` compares only `before.ownerId`. Where the two
diverge (legacy documents, or after a sponsor rebind) the billing sponsor gets a
full owner UI whose every management write is refused with a generic error.

### F-new-7 🟨 Smaller confirmed observations

- **`calculateMonthlySavingsFlow` clamps `net` at 0.** A month with 100 in and
  900 out reports `net: 0`. `deposits`/`withdrawals` are exposed separately so
  nothing is hidden, but any consumer reading `net` alone understates a
  drawdown month.
- **`parseAmountInput('1e5')` returns `15`.** Scientific notation is silently
  mangled rather than rejected. Harmless in practice (nobody types it), but
  it is the one input in the matrix that produces a *plausible wrong number*
  instead of `NaN` — everything else (`1 234,56`, `1.234,56`, `١٢٣٤`, `12٫5`,
  `٠٫٥`) parsed correctly.
- **Period close/reopen has no `AreaRestricted` equivalent for editors.**
  `ClosedMonthBanner` shows the reopen button for `workspace === 'personal' || isOwner`,
  which matches `monthUpdateAuthorized()` requiring `access.owner` — client and
  server agree. Good; noted so it isn't "simplified" later.
- **The money engine itself is clean under adversarial probing.** Verified by
  execution: cash is conserved across add → edit (amount *and* place change) →
  delete (returns exactly to `{6000,3000,1000}`); overdraw and over-transfer
  both raise `MoneyInvariantError`; envelope splits sum exactly to income at
  10000, 9999, 3333.33, 1, 0.5 and 0 with the savings envelope absorbing the
  remainder. Recurring-bill carry produced `fixed-occurrence-<template>-<period>`
  ids, reset `status` to `planned` and `paidAmount` to 0, was idempotent on a
  second run, and correctly excluded the non-recurring bill.

## B.2 New security findings

- **S-new-1 (M)** — `/api/barcode/lookup` keeps a **private in-memory limiter**
  (`hitsByIp`, route.ts:68) instead of the shared `isRateLimited()`. On
  serverless that means 60/min *per instance*, reset on cold start, and it never
  becomes durable when Upstash is configured. It is also the only public route
  with no `checkArcjet()`, and each miss can fan out to five upstream hosts for
  up to 12 s. *Fix:* `await isRateLimited('barcode', ip, 60, 60_000)` + Arcjet.
- **S-new-2 (M)** — `/api/contact` dedupe (`seenRequestIds`, route.ts:34) is a
  module-level `Map`, so a retry landing on another lambda sends a second email.
- **S-new-3 (M)** — **invite acceptance is case-sensitive on email.** Rules
  compare `resource.data.email == request.auth.token.email` verbatim; the client
  lowercases on write (`household-context.tsx:359`) and on query (`db.ts:1756`).
  Firebase does not guarantee a lowercased `email` claim for every provider or
  import path. A token carrying `Foo@Example.com` makes invite discovery return
  nothing and the accept batch deny — indistinguishable from an expired invite,
  with no way for the user or support to diagnose it. *Fix:* compare
  `request.auth.token.email.lower()` in the three `householdInvites` rules and
  the `members` `get` rule.
- **S-new-4 (L)** — `img-src 'self' data: https:` allows any HTTPS image origin.
  Avatars accept provider `https://…` URLs, so this can be narrowed.
- **S-new-5 (L)** — `verifyFirebaseIdToken` fails open on revocation-check
  transport errors (documented, bounded by `exp`; fine for an email endpoint).
- **S-new-6 (L)** — `/api/client-errors` forwards sanitized reports to
  Sentry/Better Stack when keyed; the privacy page documents analytics consent
  but not error telemetry.

**Confirmed good:** no secrets in the browser bundle; no `firebase-admin` or
service-account key in the app runtime; HSTS+preload, `nosniff`, COOP
`same-origin-allow-popups`, CORP `same-origin` with a deliberate carve-out for
social/icon assets; private routes `private, no-store`, `/api/*` `no-store`; the
service worker never caches `/api`, Firestore, Auth or identity traffic; contact
form has honeypot + per-IP limit + Arcjet + HTML escaping + a hard refusal to
send from the Resend sandbox domain in production; `npm audit --omit=dev` is a CI
gate that distinguishes a real advisory from an unreachable advisory service.

## B.3 RBAC audit

**The model.** Client (`household-rbac.ts`): 11 areas × 4 levels, clamped by
`sanitizePermissions()` against `AREA_LEVEL_OPTIONS`, resolved by
`resolveAreaAccess()`. Server (`firestore.rules`): `validCustomPermissions()`
mirrors that table key-for-key, and `customMonthChangesGranted()` enforces
per-area grants on the shared month document by diffing `affectedKeys()`.

Cross-checked and **consistent**: members/settings never exceed `view`;
invoices tops out at `editOwn`; month edits require `editAll`; entitlement lapse
downgrades to read-only while **preserving exports**; escalation to `owner` via
update is refused (`before.role != 'owner'`); a custom member cannot join with
self-authored grants (`invitationJoinOk` requires `permissions == invite.permissions`).

**Findings:**

- **R1 (M)** — `invoices: 'view'` grants a custom member the *whole* household
  queue, including every other member's `receiptUrl` (base64 image up to 120 KB).
  Documented as intentional, but it is the broadest read a non-editor can hold
  over the most sensitive artifact in the app.
- **R2 (M)** — the contributor `members`-list denial. Mechanics in **F-new-4**.
  *Fix, both sides:* rules — allow `list` for any active member (or have the
  client use the already-permitted own-row `get`); client — resolve `myMember`
  via `getHouseholdMember()` (exists, `db.ts:1376`) and only list the roster
  when `canViewArea('members')`.
- **R3 (M)** — `isOwner` derivation, see **F-new-6**.
- **R4 (L)** — `profile` role is accepted by rules' member-create branch but
  absent from `InviteRole`; `permissionsFor('profile')` falls through to
  `none()` implicitly. Make it an explicit early return.
- **R5 (L)** — `LEGACY_CUSTOM_FALLBACK` (`invoices: 'editOwn'`) is client-only;
  rules read `permissions.get(area,'none')` and grant nothing. Same class as R2:
  UI offers an action the server refuses.

# PART E — Household creation refused for an entitled Pro user (2026-09-04, follow-up)

**Reported:** a user with a valid launch-trial Pro profile could not create a
household. The UI showed only the generic error.

## Root cause: the rule was over Firestore's expression budget

Not an authorization failure. `memberCreateAuthorized()` OR-ed three branches
into a single expression; because the rules engine **inlines** every function
call into the caller, the folded cost was ~1034 expressions against a hard
**1000-expression per-request cap**. The engine refuses an over-budget request
outright, with a bare `permission-denied`, *before evaluating any branch* — so
the founding owner (who needs only the household root) was being charged for
the invitation machinery of a branch that could never apply to them.

Household creation is a batch: `households/{id}` + `households/{id}/members/{uid}`.
The root write was fine; the membership write was refused for arithmetic
reasons. The profile in the report is genuinely entitled — verified by running
the client gates against it: `resolveProEntitlement` → `isPro: true`,
`daysRemaining: 90`, `isProUser` → true, `buildHouseholdSponsorBinding` →
`bindable: true` with a projection matching the profile key for key. Every
client gate passed; the server refused on cost.

**Why no test caught it.** `tests/schema-migrations.test.ts` pinned
`memberCreateAuthorized` to a recorded bound of **1100** — above the 1000 the
engine enforces. The suite was green while the write was impossible.

## Fixes

1. **Split `memberCreateAuthorized` into three `allow create` statements** —
   `memberCreateSelfOwner` (177), `memberCreateByOwner` (691),
   `memberCreateByInvitee` (925). Firestore ORs matching `allow` statements of
   the same method and budgets each independently, so the authorization surface
   is unchanged while household creation drops from **1088 → 177**.
2. **Split `memberUpdateAuthorized` (1283) the same way** — it was over the cap
   too, which would refuse every membership edit including a member leaving:
   `memberUpdateByOwner` (727), `memberUpdateRetireInvited` (148),
   `memberUpdateLeave` (75), `memberUpdateRejoin` (962).
3. **The budget test now asserts the engine's real cap** for all seven
   membership rules (`cost < 1000`) instead of a recorded high-water mark.
4. **Emulator regression test** reproducing the exact batch — a launch-trial
   Pro profile creating a household plus its owner row — with a companion case
   proving a self-authored `owner` row in someone else's household is still
   refused.
5. **`convertToHousehold` no longer swallows the error.** The bare `catch {}`
   is why this went undiagnosed: the console was empty. It now logs the cause
   and still shows the generic notice.

## Still over the cap (known debt, unchanged here)

`monthUpdateAuthorized` (1574) and `householdMonthGate` (1288) exceed 1000 on
their **worst-case** branch. `||` short-circuits, so owner/editor writes — which
resolve before the custom-member per-area diff — complete in practice; a custom
member's month write is the branch at risk. I prototyped the same split and
reverted it: it needs `householdAccess()` to be decomposed, and unlike the
membership rules I cannot validate that here (`npm run test:rules` needs a JVM).
It is filed rather than guessed at, and the budget test keeps both pinned so
they cannot grow.

**Deploy note:** these are rules changes. They take effect only once
`firestore.rules` is deployed — the CI `deploy-rules` job, or
`firebase deploy --only firestore:rules`. The emulator suite must pass first.

# PART F — Import, sync and workspace deletion all refused (2026-09-04, follow-up 2)

**Reported, after deploying the Part E rules:** cannot import data during
onboarding of a new workspace; cannot sync; cannot delete the workspace. The UI
said the published rules "cannot store a household plan owner" and told the user
to redeploy — which they had already done.

## Same root cause as Part E, in the rules Part E did not split

Part E fixed the *membership* rules and explicitly deferred the month rules as
known debt. That debt was the remaining bug:

| Rule | Cost | Cap |
| --- | --- | --- |
| `monthUpdateAuthorized` | **1574** | 1000 |
| `householdMonthGate` (create) | **1288** | 1000 |

Every one of the three symptoms is a month write. Import creates month
documents; sync replays month updates from the outbox; teardown deletes them.
All three were refused on arithmetic, before any authorization branch ran.

**The error message was actively misleading.** `m.sync.rulesBehind` is the
*fallback* for a denial the client cannot attribute to the plan, the membership
or the sponsor — but it was worded as a specific diagnosis ("cannot store a
household plan owner… redeploy"). Redeploying was the one thing that could not
help, because the deployed rules were the current ones.

## Fixes

1. **Split the month rules by writer kind and by what the write does.**
   Firestore ORs matching `allow` statements of the same method and budgets each
   independently:

   | New rule | Cost | Covers |
   | --- | --- | --- |
   | `monthOrdinaryUpdateByFinanceWriter` | **986** | owner/editor edit to an open period — import, sync, every normal edit |
   | `monthCreateByFinanceWriter` | **902** | owner/editor bootstrapping a month |
   | `monthCreateByCustomMember` | **885** | custom member bootstrapping a month |
   | `monthUpdateByCustomMember` | 1293 | custom member edit (still over; see below) |
   | `monthCloseReopenByOwner` | 1182 | closing/reopening a period (still over) |

2. **Two purpose-built facts records instead of one.**
   `monthFinanceWriterFacts` (owner/editor/paid) and `monthCustomWriterFacts`
   (custom/permissions/paid) replace `householdAccess()` on these paths. Rules
   evaluate every field of a returned map, so the all-purpose record charged
   each branch for questions it never asked — that is what put them over.
   The sponsor is `let`-bound before being asked about, because passed inline it
   is re-expanded at each of `userProfileData()`'s uses.

3. **Deleted the superseded gates** (`monthUpdateAuthorized`,
   `householdMonthGate`, `monthWriterOk`) rather than leaving them unused, so a
   future rule cannot call one and silently re-inherit the cost. A test asserts
   they stay gone.

4. **`handleFirestoreError` no longer discards the Firestore error code.** It
   preserved only a generic message, so callers gating on `permission-denied`
   could not tell a refusal from a network blip — which is why a refused
   teardown surfaced as the wrong cause. The code and the original error are now
   carried on the rethrown error.

5. **Reworded `sync.rulesBehind`** (en/fr/ar) to say what is actually known: the
   write was refused, the app cannot attribute it to plan/membership/workspace,
   a rules mismatch is the *usual* cause, and local changes are safe. It no
   longer asserts a specific stored-field diagnosis it cannot support.

6. **Tests.** The budget test now holds `monthOrdinaryUpdateByFinanceWriter`
   and both create rules to `cost < 1000` alongside the membership rules. New
   emulator cases walk the exact reported sequence — import a month, flush an
   ordinary edit, delete the months and the household — plus an editor edit, and
   negative cases proving a viewer, a contributor and a non-member are still
   refused.

## PART G — the two symptoms that survived the first deploy

Both reports after deploying were real, and neither was a stale ruleset. They
had different causes, and only one of them was in the rules at all.

### G1. Deleting a workspace — a client ordering bug, not a rules bug

`allow delete` on a household `ledger/{mutationId}` row (`firestore.rules`
~L1347) permits the delete only once the document the row describes is already
gone: for `monthKey == 'savings'`, `!existsAfter(households/$(hid)/data/savings)`.
That rule is correct — it stops an audit row being erased while the balance it
justifies still stands.

`deleteHouseholdWorkspace` (`src/lib/db.ts:1361`) tore the workspace down in the
order `months → invoices → ledger → data/savings → members → root`. Each
`deleteDoc` is its own request, so `existsAfter` reflects live state at that
moment. When the ledger sweep ran, `data/savings` was still present, so **every
savings-kind ledger row was refused** — and, in that order, could never become
deletable. The first one threw, teardown aborted, and the UI showed
`household.genericError`.

**Fix (client):** delete `data/savings` *before* the ledger sweep —
`months → invoices → data/savings → ledger → members → root` — with a comment
marking the order as load-bearing. No rules change. A new emulator case pins the
dependency: the savings ledger row is refused while `data/savings` exists and
accepted once it is gone, so the order cannot be shuffled back.

### G2. Sync — the *recommended repair* was itself over the cap

The sync card tells a locked-out owner to run "Restore shared access", which
writes the household root. That went through `householdUpdateAuthorized`, at
**1061** — over budget. So the one repair the app offers could never succeed,
which is why the card kept re-recommending it after the user had already tried
it, and why the failure kept surfacing as the unattributable-denial message.

**Fix:** split into a shared `householdUpdateShapeOk` (**268**) plus two
independent `allow update` statements — `householdConfigUpdateOk` (**608**) and
`householdSponsorRepairOk` (**754**). Firestore ORs statements of the same
method and budgets each separately, so the authorization surface is identical
and both branches now evaluate. The redundant `householdOwner(hid)` re-fetch is
gone: the stored owner is already in `before`.

### G3. `monthCloseReopenByOwner` — 1182 → 923, now under the cap

Ownership is recorded on the household root, so this branch no longer resolves a
membership row at all: it reads the root once and checks `ownerId` and the
sponsor's entitlement. Editor and custom grants are irrelevant to a branch only
an owner can take, and rules evaluate every field of a returned facts map, so it
was paying for answers it never read.

### G4. The budget check now fails the build

`scripts/rules-budget.mjs` printed costs but only ever exited 0 — the very
regression class behind both incidents was unenforced. It now exits non-zero on
any rule over 1000, with a ratchet allowlist naming the single tolerated rule and
its bound, so a listed rule that *grows* also fails. Verified against a seeded
regression. CI already invokes the script, so this is live.

## Still over the cap (reduced, tracked)

`monthUpdateByCustomMember` (**1281**) is now the only one; `monthCloseReopenByOwner`
is down to 923 (G3). It is reached only after the cheaper statements decline, and
`||` short-circuits, so it affects only households using custom roles **with
partial month grants** — a member granted `editAll` everywhere is authorized by a
statement above it. Cutting it further means
trimming `validMonthDocument` (284), which validates document shape and
cardinality — I am not willing to weaken that to buy budget without the emulator
to prove the result. Both are pinned by the budget test so they cannot grow.

**Deploy:** `firebase deploy --only firestore:rules`, after the emulator suite
passes in CI.
