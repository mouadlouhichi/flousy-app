**Date:** 2026-08-31 · **Branch:** `arena/01a059dc-flousy-app` @ `2c1e4c3` · **Scope:** entire app (34,770 LOC in `src/`, `firestore.rules`, `messages/`, `public/`, config, CI)

## Verdict

Architecture and engineering intent are **well above average** for an indie app (static app shell + edge caching, hand-written security rules with caps, code-split i18n/Firebase, hardened avatar pipeline, honest marketing copy, a real test suite). The problem is not the design — it is that **several "security/production hardening" decisions actively break user-facing features**, and the **payment + plan model is a client-side illusion**.

Seven things I'd fix before anything else:

| # | Finding | Why it's first |
|---|---|---|
| 1 | `Permissions-Policy: camera=()` blocks `getUserMedia` | The headline Pro feature (**barcode scanning**) cannot work in any deploy |
| 2 | Self-grantable `plan: 'pro'` + fake card form shipped to prod | Free Pro for anyone; users are typing card numbers into a mock checkout |
| 3 | `households/{hid}/members` create rule has no role/email/invite check | Any signed-in user with a household ID can make themselves **owner** of it |
| 4 | Canonical + hreflang point at `https://flousy.app` (`/en`,`/fr`,`/ar` are 404) | You are telling Google your pages live on a domain that isn't your deployment |
| 5 | `LocalizedDocumentTitle` overwrites `document.title` on `/` | The keyword-rich homepage title is destroyed after hydration |
| 6 | `CI` red: `tests/blueprint.test.ts` fails at HEAD | Blocks every PR and hides all other regressions |
| 7 | `/privacy` + `/cookies` promise things the code contradicts (analytics "off until you agree", "we don't ask for card numbers") | A published privacy policy that the app violates is the worst kind of finding — legal, not technical |

## P0 — Security

### S1. Household membership is self-grantable → cross-tenant read/write of budgets
`firestore.rules:68`

```
allow create: if householdOwner(hid) || (memberId == request.auth.uid && request.resource.data.userId == request.auth.uid);
```

The second clause exists so an invitee can create their own membership doc (used by `acceptHouseholdInvite`, `src/lib/db.ts:545-570`). It does **not** check `role`, `status`, `email`, or that an invite exists. Any signed-in user who knows a household ID can write `households/{hid}/members/{theirUid}` with `{ role: 'owner', status: 'active' }` and instantly pass `householdMember()` / `householdEditor()` for that household — reading and rewriting `months/*`, `data/savings` and `invoices/*`. Realistic attacker: a partner who was removed from the workspace (`status: 'inactive'`) — they keep the ID forever.

Fix: make acceptance invite-mediated. Require the incoming doc to match an existing pending invite:

```
allow create: if householdOwner(hid)
  || (memberId == request.auth.uid
      && request.resource.data.userId == request.auth.uid
      && request.resource.data.role in ['editor','viewer','contributor','custom']
      && request.resource.data.status == 'active'
      && request.resource.data.email == request.auth.token.email
      && existsOne(/databases/$(d)/documents/householdInvites,
             i => i.data.householdId == hid && i.data.email == request.auth.token.email
                  && i.data.status == 'pending'));
```

(plus a `get()`-based expiry check, or move acceptance to a Cloud Function / Callable.)

### S2. Pro plan is client-writable — and the paywall is checked client-side
- `firestore.rules:22-23` explicitly lets the account owner set `plan` to `'pro'`.
- `src/lib/pro-features.ts:41-52` resolves entitlement as `profile.plan === 'pro'`.
- `src/lib/household.ts` (`isProFeatureUnlocked`) unlocks **every** Pro feature for anyone in a `household` workspace — and `households` creation requires only `users/{uid}.plan == 'pro'` (`firestore.rules:57`), which S2 makes trivially true.

One browser-console `updateDoc(doc(db,'users',uid), {plan:'pro'})` = all Pro features, forever. This is acknowledged in a code comment as "payments are mocked", but the mock is wired to production behaviour (see F7).

Fix order: (a) treat `plan` as read-only in rules; (b) write it only from a payment webhook with the Admin SDK; (c) until then, gate the entire upgrade UI on `NODE_ENV !== 'production'` and remove the card step (see F7).

### S3. `/api/household-invitations` is an unauthenticated email relay
`src/app/api/household-invitations/route.ts`

- No `await auth` check, no session/Firebase ID-token verification, no CSRF origin check, no rate limit, no idempotency.
- Verified live: `POST /api/household-invitations` returns a real response for an anonymous caller (503 here only because `RESEND_API_KEY` is unset in this sandbox; with the key set it **sends**).
- Anyone can send unlimited, arbitrary-address emails signed as `SmartJib <…>` and burn your Resend quota / domain reputation. Combined with the missing SPF/DMARC records your own `SEO_TODO.md` lists as open, the `From` is also trivially spoofable by others.
- `householdName` is attacker-supplied free text interpolated into the email body (escaped for HTML, so no injection — but it *is* a phishing-content vector).

Fix: verify the Firebase ID token (`getAuth(admin).verifyIdToken`), require the caller to be `householdOwner` of the invite's household, validate that the invite doc exists and is pending, cap sends per uid per hour (Vercel `@vercel/kv`/upstash or an in-memory bucket as a floor), and set up SPF + DMARC before launch.

### S4. CSP is `script-src 'self' 'unsafe-inline'` with no nonce
`src/middleware.ts:44-52`. `'unsafe-inline'` was traded for static prerendering (the comment explains it), which is defensible — but it removes the main XSS mitigation while the app renders user-supplied strings (expense names, notes, household/member names, product names from Open Food Facts) and `<script type="application/ld+json">` blocks. `style-src 'unsafe-inline'` too.

Also: the middleware matcher (`src/middleware.ts:106`) excludes `/api`, so **API responses get no CSP at all** (they do get `next.config` headers).

Fix: keep static HTML, but move to `script-src 'self' 'strict-dynamic'` + one hash per `<script type=application/ld+json>` (`next/headers` isn't needed for hashes — they're content-derived and stable for prerendered pages). That restores meaningful XSS defence without per-request rendering.

### S5. Firestore rules are not deployable from the repo
There is `firestore.rules` and `firebase-blueprint.json` but **no `firebase.json`** and no `firestore.indexes.json`; `package.json` has no `firebase-tools` dependency or deploy script, and CI (`ci/github-actions-ci.yml`) never runs `firebase deploy --only firestore:rules`. So the audited rules are only as real as someone's last manual paste into the console — and the CI workflow itself lives in `ci/` rather than `.github/workflows/`, i.e. **no checks run at all today**.

### S6. Minor but worth listing
- `X-Content-Type-Options`, HSTS, `X-Frame-Options` etc. are applied to `/(.*)` but the CSP only in middleware → mixed provenance for the same response; consolidate into one place.
- `Cache-Control: public, max-age=31536000, immutable` on `/_next/image` (`next.config.mjs:38-41`): the optimizer URL is a function of `?url=`, so any change to a source image under the same path serves a **forever-stale** image to every visitor/CDN. Use `max-age=31536000` *without* `immutable`, or key the source path with a version.
- `Cross-Origin-Resource-Policy: same-origin` on every route (`next.config.mjs:24`) also covers `/opengraph-image`; harmless for server-side crawler fetches, but it will block embedding the OG image from another origin. Scope it to `/_next/*` + app routes.
- No security headers on `offline.html`/`public/**` beyond what `/(.*)` covers — fine; but `Permissions-Policy` (see F1) also disables the camera for the *installed PWA*.
- Password policy is `min(6)` (`src/lib/validation.ts:71`) for a personal-finance app. Raise to 10+, or better: delegate to Firebase's strength settings and add a zxcvbn-style meter.
- `src/app/api/barcode/lookup/route.ts` is well written (digits-only `code`, hardcoded hosts → **no SSRF**; no user data cached). Remaining gaps: no per-IP rate limit, and negative results are cached in a shared LRU for 5 min, so a product added upstream stays "not found" for everyone.

## P0/P1 — Functional

### F1. **Camera blocked → the barcode scanner is dead in every environment**
`next.config.mjs:21`

```js
{ key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
```

`camera=()` = "allowed for no origin", including the top-level document. `useBarcodeScanner` calls `navigator.mediaDevices.getUserMedia` (`src/hooks/use-barcode-scanner.ts:241`), which the permissions policy rejects with `NotAllowedError` **before** any user prompt. Verified served on `/` and `/dashboard`. The native `BarcodeDetector` path fails the same way (it needs the stream), so both decode strategies die and only the USB-wedge fallback survives.

```js
{ key: 'Permissions-Policy', value: 'camera=(self), microphone=(), geolocation=()' }
```

Add a smoke test that asserts the header string contains `camera=(self)` — this is exactly the class of bug a 3-line test prevents.

### F2. Household invitations: the pending-invite listener can never work
`firestore.rules:105`

```
allow list: if signedIn() && resource.data.email == request.auth.token.email;
```

Firestore evaluates `list` rules **against the query**, not per document. A rule that constrains `resource.data.x` to a value the client query doesn't provably match is rejected — this is the documented `PERMISSION_DENIED` behaviour for `where('email','==',email)` + `resource.data.email == request.auth.token.email`. `subscribePendingHouseholdInvites` (`src/lib/db.ts`) swallows it (`onData([])` in the error callback), so **invite notifications silently never appear** and no console error reaches users.

Fix: `allow list: if signedIn();` (the client query is already email-scoped; the `get` rule keeps single-doc access safe), or drop `list` entirely for this collection.

### F3. Accepting an invite never marks it accepted (rule/code disagree)
`firestore.rules:107` requires `request.resource.data.status == 'pending'` for the recipient branch, but `src/lib/db.ts:568` writes `{ status: 'accepted' }`. The write is always denied; it's wrapped in `.catch(() => {})`, so the invite row stays `pending` forever: the owner's member list keeps showing "Invited", and the accept-URL stays valid. Note the rule's *intent* was clearly "from-status must be pending" (`resource.data.status == 'pending'`), with the new status restricted to `['accepted','revoked']`.

**Status 2026-09-01 — FIXED.** Re-read `firestore.rules` and `acceptHouseholdInvite`: the rule now pins the invite's *from*-status to `'pending'` (`…/householdInvites/$(request.resource.data.inviteId)).data.status == 'pending'`) rather than the written status, and `db.ts:641-646` writes `{ status: 'accepted', acceptedAt }`. Rule and code agree.

### F4. `custom`-role invitees join with **zero** permissions
`src/lib/db.ts:545-562` builds the membership from the invite but copies only `role` — not `permissions` (`invite.permissions` exists on `HouseholdInvite`, `src/lib/household.ts:36`). `permissionsFor('custom', undefined)` returns `{}` (`src/lib/household-rbac.ts:19`), so a user you invited with a hand-tuned access matrix lands on a dashboard with **everything hidden**. One-line fix: `...(invite.permissions ? { permissions: invite.permissions } : {})`.

**Status 2026-09-01 — FIXED.** That exact spread is now in `db.ts:627-629` with a comment explaining why. The **client-side** half of this is closed. The **server-side** half is not — see F6b below: the rules still refuse the writes a `custom` member's matrix promises.

### F5. Contributor role is unreachable, but its UI is shipped
`permissionsFor()` special-cases `'contributor'` (`household-rbac.ts:19`), `localizeHouseholdRole` translates it, `contributor-invoice-form.tsx` + `household-invoice-review.tsx` implement it, and the rules grant contributors invoice access — but `HouseholdContextValue.invite` accepts only `'editor' | 'viewer' | 'custom'` (`household-context.tsx:14`), and `/api/household-invitations` rejects anything else (`role in ['editor','viewer','custom']`). Either wire `contributor` through the invite type + role select + API allowlist, or delete ~600 lines of dead feature surface.

**Status 2026-09-01 — FIXED.** Wired through, not deleted: `household-context.tsx:12` is `Extract<HouseholdRole, 'editor' | 'viewer' | 'contributor' | 'custom'>` and `api/household-invitations/route.ts:14` is `INVITABLE_ROLES = ['editor', 'viewer', 'contributor', 'custom']`. The member-claim rule allows the same four roles.

### F6. Orphaned pending member after acceptance
`acceptHouseholdInvite` creates the UID-keyed membership but never flips the email-keyed `status:'invited'` record to `inactive` (the rule even has a clause for it, `firestore.rules:73-77`, unused). Result: a permanent ghost "invited" row per accepted invite.

**Status 2026-09-01 — FIXED.** `db.ts:647-653` now retires `invite.memberId` with `{ status: 'inactive', userId, retiredAt }`, and the rule branch that permits it (`firestore.rules:132-138`, `affectedKeys().hasOnly(['status','userId','retiredAt','joinedAt'])`) is the one in use.

### F6b. A `custom` member's permission matrix is not honoured by the rules (**OPEN**)
The client now resolves access through `resolveAreaAccess()` (`src/lib/household-rbac.ts`), so a member whose matrix grants `editAll` on `expenses` gets working edit affordances. The rules do not read the matrix at all: `householdEditor(hid)` (`firestore.rules:11`) is `role in ['owner', 'editor']`, and every writable household document — `months/{key}`, `data/savings` — gates `create, update` on `householdEditor(hid)`. A `custom` member therefore sees a Save button whose write Firestore denies with `permission-denied`.

Not fixed, deliberately: the months document interleaves fields from several areas (`totalBudget` → balances, `variableExpenses` → expenses, `fixedExpenses` → fixedBills, `savingsActivity` → savings), so a correct fix needs per-field area checks comparing `resource.data` against `request.resource.data` — and **this sandbox has no JVM and no Firebase CLI**, so no rules emulator can validate the change. Shipping unverifiable rules risks locking every household out of its data. Fix it somewhere that can run `firebase emulators:exec --only firestore`.

`contributor` is unaffected: the invoice rules allow that role explicitly, and contributors are not meant to write months.

### F7. Fake card checkout is fully reachable in production
`src/components/modals/ProUpgradeModal.tsx` — steps `'plan' | 'card' | 'processing' | 'receipt'` with real inputs for card number / expiry / CVC / holder (`#pro-card-number`, lines 395-412), validation, a "Fill Demo Test Card" helper, a fake 3DS delay, and a receipt. Nothing keys off `NODE_ENV`; `receiptUrl` even points at `https://dashboard.stripe.com/test/payments/pi_mock_…` (a real Stripe URL → 401 wall for users). Two distinct harms:
1. Users enter **real PAN/CVC** into a non-payment form (state-only today — not persisted, not sent — but browser/password-manager autofill makes that inevitable). Add `autoComplete="off"` + `inputMode` guards *and* gate the whole flow, or render "Preview — no payment is taken" persistently.
2. `trackEvent('purchase', { value, currency, transaction_id })` fires a **fake conversion** into Firebase/GA (`:198-204`). If any conversion-optimised campaign ever reads this, it is bidding on imaginary revenue.

Also: `processPayment` always succeeds and there's no server receipt, so `planNextBillingDate` claims a renewal that will never happen — that is a subscription-billing misrepresentation, not just a stub.

### F8. `document.title` is clobbered client-side (and localized)
`src/components/localized-document-title.tsx:44-52`

```
'/': m.common.appName        // "SmartJib"
```

The root layout mounts this on **every** page, so after hydration the homepage title becomes `SmartJib`, throwing away `SmartJib - Free Private Budgeting & Money Tracker App`. `/about`, `/help`, `/careers`, `/contact`, `/blog` get their *eyebrow* (e.g. "About", "Help center") instead of the authored title. Google renders JS, and it is the post-hydration DOM that gets compared against your `<meta>`. Either skip the effect when `pathname === '/'` and for routes with authored metadata, or drive it off a per-route localized title map that mirrors `metadata`.

Same class of issue, public pages only: `/about`, `/help`, `/contact`, `/privacy`, `/terms`, `/cookies`, `/careers` are `"use client"` pages, so they **cannot** export `metadata` at all — no title, no description, no canonical, no OG, no `BreadcrumbList`. They fall back to the *root* metadata ("SmartJib - Free Private Budget Tracker…", `/`), which makes every legal/help page a **duplicate title+description** in the SERP and un-shareable. The fix is cheap: keep the client page as the body and add a tiny `layout.tsx` per route exporting metadata (as `login/layout.tsx` and `onboarding/layout.tsx` already do correctly).

### F9. Receipt upload can wedge a whole month document (silent data loss)
`src/components/modals/ExpenseModal.tsx:115-126` → `FileReader.readAsDataURL(file)` → stored as `variableExpenses[].receiptUrl` → serialized inside the **month document**. There is no type check, no size cap, no downscaling — and no validation on read (`<img src={receiptUrl}>`, `:443`). A single phone photo (2-6 MB → 2.7-8 MB base64) blows Firestore's 1 MiB per-document limit; `updateAndSaveMonth` reports failures with `console.error` only (`dashboard-provider.tsx:452-466`), so the expense appears saved, persists to `localStorage`, and silently never reaches the cloud — and **every subsequent edit to that month fails too**. The avatar path shows the correct pattern (`src/lib/profile-avatar.ts`: 256px resize, 140 KB cap, MIME allowlist, `isProfileAvatarSource()` on render). Reuse it for receipts, or move receipts to Storage/an on-demand blob and store a reference.

Related: `handleReceiptUpload` never resets `input.value`, so re-picking the same file does nothing.

### F10. Any local-write failure aborts the cloud write
`dashboard-provider.tsx:456` and `:471` call `localStorage.setItem(...)` **outside** try/catch and **before** the Firestore write. Safari under memory pressure / a full quota / blocked storage throws `QuotaExceededError` out of the save callback → the document is never written and the click looks like it did nothing. `src/lib/month-cache.ts:66-73` already has the safe wrapper (`writeCachedMonth`) — use it in both places.

### F11. Whole-document last-write-wins on a *shared* budget
`saveMonthBudget` / `saveHouseholdMonthBudget` replace `variableExpenses[]` / `fixedExpenses[]` wholesale from a client-held snapshot (`{merge:true}` only merges top-level fields). Two household editors (or one user on phone + laptop): the second save **erases** the other's entry with no error and no conflict UI. Also `subscribeMonthBudget`'s callback is `async` and awaits `getPreviousMonth` inside the snapshot handler (`:380-405`) → interleaved writes can persist a stale rollover. Fix: per-expense subcollection documents, or `runTransaction` + `updatedAt`/`updatedByUserId` precondition (`actorForMonth` already stamps `updatedByUserId` — nothing checks it) with a "someone changed this month, reload?" banner.

### F12. A 5-second timeout silently kicks users out of the household workspace
`household-context.tsx:38`: `setTimeout(() => setLoading(false), 5000)`; `dashboard-provider.tsx:231-235` then sees `householdLoading === false && !household` and resets `activeWorkspace: 'personal'`. On a slow mobile connection (your core audience) household users get dumped to personal with no explanation, and the reset is **persisted to the profile**. Fix: keep the subscription, don't infer "no household" from an absence of data within a window; only reset on an explicit `permission-denied`/`not-found`.

### F13. Profile-fetch failure fakes an onboarded user
`src/lib/auth-context.tsx:170-181`: on any `syncUserProfile` error the fallback profile is `onboardingComplete: true` with `currency: 'MAD'`. A transient Firestore timeout therefore (a) skips onboarding forever on that device, and (b) can silently switch a EUR user's formatting to MAD. The fallback should be "retry/empty", never a fabricated completed state.

### F14. Account deletion is unreliable and incomplete
`src/lib/auth-context.tsx:296-303` + `account-panel.tsx:73-83`:
- `await deleteAccount()` has no `try/catch` around `deleteUser(user)`, which fails with `auth/requires-recent-login` for anyone whose session is older than 5 min — the near-universal case. Result: a dead dialog, no error, "Delete my account" appears broken.
- Ordering is data-first, then auth. `deleteUserAccountData` **swallows** errors (`db.ts`, `catch { console.error }`), so partial Firestore deletes go unnoticed while the auth user is destroyed → the leftovers are permanently unrecoverable (nobody can sign in to finish the job).
- Coverage: months + savings + `products` + `sessions` + profile, but **not** `householdInvites` addressed to that email, and **not** the households the user owns. Deleting the account of a household owner freezes that workspace forever: `households` update/delete is `householdOwner(hid)`-only, so no remaining member can remove themselves, edit months, or delete anything (and their data can't be erased → a real GDPR Art. 17 problem for the *other* users too).
- Rules block deletes for any legacy month doc missing `totalBudget`/`bankPart`/… (`firestore.rules:27` uses `allow write`, which includes `delete`, and `isMoney(incoming().totalBudget)` is evaluated against the pre-delete doc) → those deletes fail silently. Split `read`/`create`/`update`/`delete` and let `delete` be owner-only.

Add: re-auth prompt (`reauthenticateWithCredential`), a per-collection result tally in the UI, a "leave/transfer households" step, and a scheduled Cloud Function for authoritative erasure.

### F15. `contributor`/`custom` labels and a blank "Paid from" for custom money sources
`src/components/dashboard/screens/courses-screen.tsx:605` does `m.places[session.place]`, but `m.places` is only `{bank, home, wallet}` while `session.place` is `MoneyPlace = string` (custom ids from `money-sources-panel`). For any user-defined source this renders `undefined` → a blank label, and it's one of the 52 `--strict` errors (`TS7053`). Every other screen resolves labels through `useMoneyPlaces().label()` or `localizePlaceName` (and `courses-bill.tsx:44` even has the `|| session.place` fallback). Use the hook here too.

### F16. Non-English users get English categories that then mis-bucket
- `src/lib/messages.ts:84` `getDefaultCategories(_language)` ignores the language on purpose → FR/AR onboarding seeds `Food`, `Transport`, `Entertainment`…
- `bucketOf()` (`store.ts:400-425`) classifies needs vs wants by **English keyword substring** (with a handful of French words bolted on: `alimentation`, `santé`, `loisirs`). A French user's `Loyer`, `Essence`, `Crèche`, `Abonnement Netflix` are not matched → `Loyer` counts as a **want**; an Arabic user's categories are never matched → the entire needs envelope reads 0.

This corrupts the core value proposition (the envelope split) for the two non-English locales you market to. Fix: store `envelope` explicitly on the category (`categoryEnvelopes: Record<string,'needs'|'wants'>`) with a UI control, and use keyword matching only as a seed default.

### F17. `onboardingComplete` self-heal can resurrect completed onboarding
`dashboard-provider.tsx:243-252`: if the local flag says done but the cloud says false, it writes `onboardingComplete: true`. Fine. The inverse path — a user who *deliberately* re-runs onboarding after `clearLocalData()` on sign-out — re-bounces them to `/onboarding` with their real data already loaded, and the onboarding page's writes (`saveMonthBudget`) will overwrite the existing month. Gate step-1 on "no month document exists", not just on the profile flag.

### F18. Import: no cap against the rules' cap; parser breaks on quoted newlines
`handleBatchImportVariable` (`dashboard-provider.tsx:665-674`) appends every parsed row with no limit; `firestore.rules:27` rejects any month with `variableExpenses.size() > 2000` → the write fails, `console.error`, and the imported rows exist only locally. Also `ImportCsvModal` splits on `/\r?\n/` **before** quote-aware parsing (`:283-296`), so RFC-4180 multi-line quoted cells (common in bank exports) shift every column; and `getCsvHeaderKind` matches by substring (`:57-65`), so `Nominal value` → `name`. Cap rows with an explicit "first 2000 only" notice, parse as a real character-state machine, and prefer exact/word-boundary header matching.

### F19. `next start` + `output: 'standalone'`
Verified warning: `"next start" does not work with "output: standalone" configuration.` Vercel ignores `output` today, so the field is a no-op that will bite the moment anyone self-hosts from `npm start`. Either drop `output` or change `start` to `node .next/standalone/server.js`.

### F20. Silent demo mode when Firebase env is missing
`src/app/login/page.tsx:118-121,134-139,146-151,163-166`: whenever `isConfigured` is false — or an error message merely contains `"not configured"` — the app calls `enableDemoMode()` and navigates to `/dashboard` **with no visible indication**. A Vercel env-var mistake (e.g. set for Production but not Preview, or an env var renamed) turns real sign-ins into local-only sessions where people happily enter months of financial data that never syncs. Fix: an unmistakable persistent "Demo — nothing is saved to your account" banner (the `demo-mode.ts` helper exists; the UI doesn't gate on it), and never fall back on a `message.includes()` test.

### F21. `firebase-blueprint.json` is out of sync → **CI is red**
```
not ok 4 - lists a path for every document written by src/lib/db.ts
  the paths in src/lib/db.ts drifted from the blueprint firestore map
  + '/households/{hid}', + '/households/{hid}/data/savings'
```
`deleteHouseholdWorkspace` (`db.ts:~480`) uses a local `hid`, which the blueprint-sync test turns into path names the blueprint doesn't declare. Fix by adding the two keys to `blueprint.firestore`, or (better) name the local variable `householdId`. Until then every PR is red and people learn to ignore the checks.

### F22. Smaller functional nits (each one real, cheap to fix)
- `getPreviousMonth`/`carryOverRecurring` use `user!.uid` (`dashboard-provider.tsx:489`) — safe today because of the `householdId || user` guard above it, but it's the only non-null assertion left in `src/lib` + `src/components/dashboard`.

## SEO / GEO / AEO / AIO

Evidence below is from the rendered HTML of the production build served locally, plus the SEOptimer report committed at repo root (audited against `flousy-app.vercel.app`).

### SEO-1. Canonical, sitemap, robots, OG and `llms.txt` all point to `https://flousy.app` — which is not the deployment
`src/lib/seo.ts:1` `SITE_URL = 'https://flousy.app'` → `metadataBase`, `<link rel="canonical" href="https://flousy.app">` (verified in HTML), `Sitemap:` + `Host:` in `/robots.txt`, every `<loc>` in `/sitemap.xml`, `og:url`, `og:image`, and all `llms.txt` links.

The committed SEOptimer report shows the audited page as **`https://flousy-app.vercel.app`** with `Canonical Tag: https://flousy.app` — a cross-domain, non-self-referential canonical. Google treats that as "consolidate everything to flousy.app and drop the Vercel URL from the index". `flousy.app` resolves to Cloudflare (`104.21.0.232`, `172.67.128.96`); I could not fetch it from this sandbox (no outbound 443), but the report's sitemap line references `flousy.net`, an unrelated Arabic top-up/bill-payment site — **please verify what `flousy.app` actually serves before anything else in this section.** If it is parked, 404s, or a different business, you are canonicalising your entire site to someone else's domain, and the name collision ("Flousy"/"فلوسي" = money) also contaminates the SmartJib brand entity.

Two coherent options:
1. Own the domain: serve the app at `https://flousy.app` (Vercel domain + redirect `*.vercel.app` → apex with 308), keep `SITE_URL`, and add a `robots.txt` on the Vercel host or `X-Robots-Tag: noindex` for it — but 308 is enough.
2. Deployed-domain-agnostic: derive `SITE_URL` from `VERCEL_PROJECT_PRODUCTION_URL`/`HOST` at request time in `robots.ts`/`sitemap.ts`/`metadata` (`await headers()`), so the canonical always matches the origin that served the document. For a public marketing site this means those routes become dynamic — accept it, or build one sitemap per hostname at deploy time.

Do **not** leave it as it is: it's the single highest-leverage SEO fix here.

### SEO-2. The hreflang cluster is invalid in full
`src/app/page.tsx:36-43` emits:

```html
<link rel="alternate" hreflang="en" href="https://flousy.app/en">
<link rel="alternate" hreflang="fr" href="https://flousy.app/fr">
<link rel="alternate" hreflang="ar" href="https://flousy.app/ar">
```

Verified: `/en`, `/fr`, `/ar` → **404**. There is no locale routing anywhere in the app — `fr`/`ar` are client-side `localStorage`/cookie swaps (`src/lib/i18n.ts:60-77`). Three separate problems: the cluster's URLs don't exist; the self-reference is missing (`/` must be in its own cluster); and there's no `x-default`. Google ignores an incomplete/invalid cluster — you pay the markup for zero benefit, and you signal a multilingual site you don't have.

### SEO-3. Localized content exists but is invisible to every crawler — the real GEO/AEO gap
`src/lib/blog-locales.ts` (409 lines) holds complete French and Arabic editions of the blog, selected client-side at a **single** URL. So:
- Google indexes only the English edition; FR/AR editions are 100% organic-invisible.
- The Arabic app UI is served from `<html lang="en" dir="ltr">` (`src/app/layout.tsx:112-113`, mutated post-hydration) → wrong-language signals for RTL users, a flash of LTR layout (CLS), and screen readers mispronouncing Arabic until hydration.
- LLM/AI crawlers that don't execute JS (most of Perplexity/ChatGPT-Oz/Cline-class fetchers, and Google's non-rendering fetches) see only English.

For a Morocco-first product with an RTL locale this is the difference between "supported in 3 languages" and "discoverable in 1". Route it: `/fr/...`, `/ar/...` (or `/en` as default + `x-default`), make the pages server components reading the `flousy_language` cookie you already set, emit self-referential canonicals + a real hreflang cluster + `og:locale:alternate`, and set `lang`/`dir` on the server (`middleware.ts` can read the cookie — you already have `getLocaleFromCookieString`) so nothing flickers.

### SEO-4. The FAQ JSON-LD is English-only while the visible FAQ is localized
`src/app/page.tsx:84-95` builds `FAQPage` from `LANDING_FAQS` (`src/lib/seo.ts:45-84`), but the rendered accordion comes from `m.landing.faq.items`. For FR/AR visitors the markup no longer matches the visible content — Google's FAQ guidance ("content must be visible on the page") explicitly disallows that, and duplicated FAQ data in two files is a drift hazard (they match today; nothing tests it). Add `LandingFaq` to `messages/*.json`, feed both from there, and add a parity test (`message-catalog-parity.test.ts` is the right home).

### SEO-5. Structured data: right shape, missing pieces
`SoftwareApplication` has no `softwareVersion`, no `datePublished`/`dateModified`, no `featureList`, no `screenshot`, and `offers` only describes the free tier (`price: '0'`) while the page renders a **$4.99/mo / $39.99/yr Pro plan** (`payments.ts:57-61`, used by `ProUpgradeModal`). Add an `Offer[]` for both tiers with real `price`/`priceCurrency`, and mark availability. Missing entirely: `WebSite` (+`SearchAction` is N/A), `BreadcrumbList` on the landing/`/blog` index (only article pages have it), `HowTo` for `how-it-works-section.tsx` (prime AEO/AI-overview fodder), `Organization.sameAs` (the profiles don't exist yet — see `SEO_TODO.md`), and `Organization` lacks `contactPoint` (support email is on `/contact` as plain text: `careers@flousy.app` is even hard-coded in `src/app/careers/page.tsx:20` and must move to config).
`Organization` is emitted with only `name`/`url`/`logo` — enough for the SEOptimer "Identity Schema: Organization" tick, too thin to build an entity. Consider a `Person` for the founder + `about`/`mentions` on `/about`.

### SEO-6. `sitemap.xml` `lastmod` is fabricated and stale
`src/app/sitemap.ts:5` `const lastModified = new Date('2026-07-28')` for 8 of 11 URLs, while today is 2026-08-31. Google explicitly ignores `lastmod` it doesn't trust, and a *wrong* one is worse than none. Use the build timestamp (`new Date()` in `sitemap.ts`, which runs at build) or per-route real dates, and set `<changefreq>` honestly. Also missing from the sitemap: `/login`-adjacent public entries are fine to omit, but `/offline.html` should be excluded (it is — OK) and every locale variant must be added when SEO-3 lands.

### SEO-7. Marketing routes carry the root metadata
See F8: `/about`, `/help`, `/contact`, `/privacy`, `/terms`, `/cookies`, `/careers` have no `<title>`/`description`/canonical/OG of their own (client components can't export `metadata`). Verified: `/blog` and `/blog/[slug]` do it right, and the blog pages are the only routes with per-page metadata + `BreadcrumbList`/`BlogPosting`. `/blog/[slug]` also correctly sets `dynamicParams = false` and returns `notFound()` — good.

### SEO-8. Two brand names are live at once
Code/`llms.txt`/JSON-LD/`appleWebApp.title`/manifests = **SmartJib**; the SEOptimer capture of the deployed site shows `Private Budget Tracker | Flousy`; the repo/README/`flousy.app`/`flousy_*` storage keys = **Flousy**. The rebrand is in the source but not (fully) in the deployed index. Decide one, deploy it, and add `Organization.alternateName: "Flousy"` so the old name keeps pointing at you. Local storage keys and the `flousy_language` cookie can stay (rename only with a migration reader).

### SEO-9. No measurement, and no consent — both matter
SEOptimer: *"We could not detect an analytics tool installed on your page."* Firebase Analytics is deliberately lazy (`src/lib/analytics.ts`), so no `page_view` is sent unless something calls `trackEvent`, and `FirebaseAnalytics` (mounted in `app-providers.tsx`) only exists on `/login`, `/onboarding`, `/dashboard` — **the marketing site is uninstrumented**, so the funnel you're doing all this SEO for is unmeasurable.

Simultaneously, every `trackEvent` — including `login`, `sign_up`, `purchase` — initializes `firebase/analytics` and fires with **no consent state at all**: no `setConsent({ analytics, ad_storage })` anywhere in `src/lib/analytics.ts` (verified: `getAnalytics(app)` is called as soon as `isSupported()`), no banner, no gate — while `/privacy` §4 states analytics "is **off by default until you agree to it**" and `/cookies` §3 says the same (see **L1** below). Google requires **Consent Mode v2** for EEA/UK traffic (enforced since March 2024), and ePrivacy/GDPR require prior opt-in for non-essential storage. Implement `setConsent({analytics:false, ad_storage:false})` before `getAnalytics()`, a minimal banner (the app already writes `flousy_language`, `flousy_authed`, `sidebar_state` cookies + localStorage), and a `/cookies` preference centre wired to the consent state. Also: `localStorage` holds budget amounts, profile JSON, household ids and plan flags — personal data — and neither `/privacy` nor `/cookies` discloses it or the third parties actually touched (`identitytoolkit.googleapis.com` + `firestore.googleapis.com`, `*.firebaseapp.com` for auth popups, Resend for invitations, and **Open Food Facts**, which receives every scanned barcode per `src/lib/product-lookup.ts`).

### GEO/AEO/AIO — what's genuinely good here
Credit where due, because it's rare and it should be preserved:
- **`public/llms.txt` exists**, is factual, numerically consistent with the product (12 currencies, 4 strategies, manual entry, no bank connection) and lists deep links into `/blog` — the exact structure AI answer engines cite. Keep it in sync via a test.
- **Copy is honest**: metrics are `4 styles / 3 places / 12 currencies / ~2 min`, not invented social proof; `FLOUSY_FACTUAL_DESCRIPTION` (`seo.ts:36`) is a single canonical, quotable, entity-rich sentence reused verbatim across `llms.txt`, FAQ answers and the What-is section — that's textbook answer-engine optimization.
- `security` section claims only what the code does (Firestore rules isolation, no bank connection, no ad profiles, export, deletion) instead of "bank-grade 256-bit encryption / SOC 2" boilerplate.
- SEOptimer: GEO "very good", AI crawlers explicitly not blocked, 1154 words with no missing `alt`, no missing `h1` (verified `h1` count = 1 on all 8 public routes), JSON-LD present, `robots.txt` present, SSL + HTTPS redirect, prerendered HTML so rendering-dependent crawlers aren't needed (report: rendering 1%).

Add for AIO completeness: `llms-full.txt` (or a `/blog/atom.xml`), an `updatedAt` line in `llms.txt`, `/llms.txt` linked from `layout.tsx` (`<link rel="llms">` is informal but harmless), quoted-stat sentences LLMs can lift (the "~2 min setup", "12 currencies"), and — highest value — **make the FR/AR editions crawlable** (SEO-3), since no markup fixes content that only exists after JS.

## Follow-up found in review: invitation mail on Vercel

A preview deployment returned `503` for `POST /api/household-invitations`
("mail not sent") because Vercel scopes environment variables per environment:
`RESEND_API_KEY` existed only for Production, and an existing deployment keeps
the environment it was built with. Fixed as follows.

- **Do not hide it.** The panel used to fall back to "share the code" on any
  failure; it now reports `invitationUnavailable (503)` and logs the reason.
- **Stable codes** on every failure path (`email_not_configured`,
  `sandbox_sender`, `unauthorized`, `session_expired`, `rate_limited`,
  `invite_not_found`, `delivery_failed`, …) plus a `hint` naming the variable to
  set, so the response body explains itself.
- **Preview must not be blocked by a production guard.** The sandbox-sender
  refusal keyed on `NODE_ENV`, which is `production` on Vercel previews too — so
  even after adding a key, previews refused to mail. It now keys on `VERCEL_ENV`.
- **`GET /api/household-invitations`** reports `emailConfigured`,
  `sandboxSender`, `environment` and `code` without sending anything, so
  configuration is checkable from a terminal instead of the function logs.
- **Accept link** is built from `APP_URL` → `NEXT_PUBLIC_SITE_URL` → the Vercel
  deployment URL, never from the request's own `Host` header.
- **The 401 that followed was this branch's bug, and it is fixed.** Identity
  Toolkit's `accounts:lookup` is a POST that requires the project's `key=`, and
  the check called it as a GET without one — so every caller failed
  verification, and the "requires a signed-in caller" gate rejected logged-in
  users too. Identity is now established by verifying the token's RS256
  signature and `iss`/`aud`/`exp`/`sub` against the certificates Firebase
  publishes (`src/lib/firebase-id-token.ts`, covered by
  `tests/firebase-id-token.test.ts` including `alg:none`, claim-tampering,
  revocation and certificate-endpoint outage), with the API-key lookup kept only
  as an optional revocation refinement that fails open when unreachable. A
  deployment missing `NEXT_PUBLIC_FIREBASE_PROJECT_ID` answers
  `auth_not_configured` (503) rather than pretending nobody is signed in.

Setup: `vercel env add RESEND_API_KEY` for Production **and** Preview, a verified
`RESEND_FROM_EMAIL`, then `vercel redeploy`. Without those, household invites
still work — the code path is unaffected.
